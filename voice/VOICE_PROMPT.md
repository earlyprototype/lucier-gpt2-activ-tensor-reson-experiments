# Voice prompt: how to write for Thom and for this repo

This is the standing instruction set for anyone (human or AI) writing chat
replies, reports, issues, PR text, or documentation for this project. It
consolidates the working agreements from `docs/sessions/SESSION_03_HANDOVER.md`
and the rules sharpened during the 2026-07-31 alignment sessions (issue #106).
A previous session was ended for violating these rules. Treat them as
non-negotiable.

## The reader

Thom is a designer by background, learning the mathematics earnestly and
fast. He has no formal ML background and does not need one to be the final
authority on this project: he is the operator, and the record answers to him.
He values honest null results and caveats exactly as much as positive
results. Never condescend, and never pad.

## The ten rules

1. **Plain language only.** Write as if to a smart person with no machine
   learning background, because that is who is reading. When a question is
   asked, answer it from zero.

2. **Never use a bare identifier.** F8, M3, H4, run 17, ν: none of these
   may appear without being defined in ordinary words in the same sentence.
   Wrong: "H4 is not supported." Right: "H4, the old prediction that each
   attention head's settled state could be computed from its weight matrix
   alone, is not supported."

3. **Never use a bare statistic.** A number needs its meaning attached in
   the same sentence. Wrong: "97/125 (77.6%)." Right: "97 of the 125 noise
   trials, about three quarters, ended in the same destinations the language
   prompts reach."

4. **Use the correct technical terms, defined on first use.** Attractor,
   basin, fixed point, limit cycle, residual stream, argmax, entropy: these
   are welcome, each with a one-clause plain definition the first time it
   appears in a piece of writing. Terms of art (weights, heads, attention)
   get the same treatment.

5. **No decorative metaphors.** The bell, the chord, ringing, timbre, and
   their relatives read as noise, not aid. The one exception is the README:
   it is "the piece," its voice is Thom's, and its imagery is his call.

6. **No em dashes, ever, in anything written for Thom or the repo.** This
   is a standing pinky promise. Use colons, commas, parentheses. Verify with
   a grep before committing (note: `grep -c` returns exit code 1 on zero
   matches, so do not chain it with `&&` in front of git commands).

7. **Lead with the outcome.** The first sentence of any reply or report
   answers "what happened" or "what did you find." Supporting detail comes
   after, for readers who want it.

8. **Keep it short, but never at the cost of clarity.** Cut details that do
   not change what the reader would do next. Do not cut the definitions,
   and do not compress prose into fragments or arrow chains.

9. **Honest numbers only.** Every number in a findings document or report
   is generated by a script from the data, never computed by hand or from
   memory. If a result is negative, say so plainly; if a claim carries a
   caveat, the caveat travels with the claim in the same paragraph.

10. **Repo conventions that carry the voice.** Descriptive multi-line
    commit messages with the findings in the body. Draft PRs. CodeRabbit
    for independent review (Thom explicitly wants independent eyes, not
    Claude reviewing Claude). The canonical scientific record is
    `docs/FINDINGS.md`; experiment reports live beside their outputs.

## The test

Before sending anything, reread it as someone who has never seen this
repository. If any sentence requires looking something up to understand,
rewrite that sentence. If a reply to a question does not answer the
question in its first sentence, rewrite the reply.
